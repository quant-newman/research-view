## 本批做了什么

### 1. B1 逐条 → 整批(src/research_view/structure.py)

#47 里留档"省得最多、有批内串扰风险、单独排期"的那条本批落地。默认 8 条/次(`B1_BATCH`),
单条正文截断 1500 字符。四道护栏:

- **规则块前置且逐字不变**:判断口径一个字没改;同时它成为公共前缀,可被平台前缀缓存复用。
- **每条带 `### i` 序号**,要求 LLM 在输出里照抄 i。
- **回写严格按 i 对齐**;越界 / 重复 / 缺 i / 条数不足 → **丢弃该条**,`llm_done` 保持 false
  下档重跑。**绝不按数组位置猜** —— 错位回写是把 A 条的数字钉到 B 条头上,属事实层幻觉,
  踩 PROCESS §8 红线,比少写一条严重得多。
- **整批失败自动拆逐条**:失败可能是某条正文有毒而非网络,拆开后最坏退回旧行为,不会
  让一个坏批把队列永久卡住。

顺带:`run_structure` 抽出 `_fetch` / `_writeback` 两个接缝(分批逻辑得以无库测试);
清掉 `_chains` / `chains` 死参 —— `_prompt` 从来没用过它。

### 2. LLM 夜间窗口(src/research_view/config.py `llm_allowed`)

只在 **UTC+8 18:00–08:00** 调 DeepSeek,白天留 09:45 / 15:15 两档补做点。

- **命中给 15min 宽限**:cron 火点到真正执行之间隔着 flock 排队(`flock -w 900`)与 ssh,
  卡死精确 HHMM 会让补做点在编排拥堵时凭空丢失。宽限 <15min 保证一个火点只命中一次。
- **窗口跨零点**,判据是 `hour >= 18 or hour < 8`,不是 and(最容易写错的一处)。
- 白天静默档:`run_light` 里 **B1 与 report_increment 整步跳过**;`hotspots` /
  `research_digest` 在模块内降级为"统计行最新 + 沿用当天上一版叙述"。
- **降级时 sig 一律置空**。这是本批第二个命门:落了指纹,夜间窗口一开就会指纹一致直接
  命中这份白天的旧叙述,门控退化成"一天只生成一次"。
- 手动补跑:`run_light.py --llm` 或 `RV_LLM_FORCE=1`。

### 3. 盘前 08:30 → 07:40(crontab)

`30 0 * * 1-5` → `40 23 * * 0-4`。**DOW 必须跟着日界一起挪**:UTC 23:40 周日–周四
= UTC+8 07:40 周一–周五。同时把日志名从 `$(date ...)` 改成 `$(TZ=Asia/Shanghai date ...)`
—— 宿主时区是 UTC,不改的话周一 07:40 的盘前日志会落进 `premarket-20260824.log`(周日的
UTC 日期),排障时对不上交易日。美股夏令时 04:00 UTC+8 收盘,07:40 隔夜数据早已就绪,零内容损失。

### 4. chat_json 窗口外只告警,不硬拦

所有生产入口本就在窗口内或已被上游门控(盘后 22:30 / 美股 21:30–05:00 / 信函周三 07:00 /
成绩单周日 20:00 / 盘前 07:40 全在窗内)。真在 `chat_json` 里硬拦,手动补跑会变成一片假失败
并污染各处降级路径(sig 置空、兜底文案落库),比它防的问题更糟 —— 告警载体教训:
兜底要可观测,不要脆断。所以只打一行 `⚠ 窗口外 LLM 调用`,让漏网的调用点在日志里现形。

## 关键设计取舍

- **为什么 hotspots/digest 不整步跳过,而是模块内降级**:热度数字、新闻计数、龙虎榜、
  主力净额全是纯 SQL,盘中该实时就得实时。整步跳过会让白天热点榜的**数字**也停在早上;
  模块内降级只冻住叙述层,统计行照旧每档重算 —— 这与 #47 的哲学一致。
- **白天不做 B1 的代价如实记**:白天新增新闻只有标题,摘要/情绪/科技筛要等下一个补做点
  或 18:00 开窗。这是使用者在三个选项里明选的,不是工地擅自缩水。
- **批量不降质**:temperature=0、规则逐字未改、每条只依据自己那条(prompt 里显式禁串扰)。
  实测见下,含 #43「百分比≠倍」护栏在批量下的复验。
